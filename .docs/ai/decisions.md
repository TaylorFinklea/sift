# Decisions

- **Server storage:** collections, runs, and decisions live on the server so devices share history: SQLite for the container and D1 for Cloudflare Workers.
- **Container authentication boundary:** the existing access proxy authenticates users. The container does not implement accounts or trust identity headers; network reachability must be restricted to the authenticated proxy. The Cloudflare runtime separately verifies signed Access assertions and the configured owner identity.
- **Proxy writes:** require one configured exact HTTPS origin and a matching same-origin `Origin` on mutations. This is a CSRF check, not user authentication.
- **Runtime portability:** built-in `node:sqlite` keeps container hosting self-contained. A separate Cloudflare entry uses D1; the original Product Design/Sites packaging entry remains intact.
- **Sort history:** each run holds an immutable copy of its card snapshot; later rounds copy only cards kept in the completed parent. Undo marks the latest decision while retaining it in the audit history.

- **2026-11-01 — Cloudflare hosting selected:** Workers with D1 is the intended cloud host; preserve the container/SQLite option. This supersedes the earlier deferred hosting choice. Local implementation/verification is approved; live resources, DNS, Access changes, deployment, and data migration await final approval.
- **2026-11-01 — Separate authentication by hostname:** main app at `sift.example.com` uses Cloudflare Access; API at `api.sift.example.com` uses named revocable bearer keys generated in the authenticated main app. No key-management authority is exposed through API keys. Store key digests, show new secrets once.

- **2026-11-01 — Optional card context:** retain `detail` as the compatible description field and add optional `pros`/`cons` arrays. Legacy snapshots default to empty lists when read; no destructive migration is needed. Structured editing preserves card IDs; old runs retain their own copied context.

- **2026-11-01 — API-key defaults:** named keys default to read-only access and 90-day expiry; the owner can explicitly choose read/write and 30-day or no expiry. All key administration stays on the Access-protected app host. Browser app requests remain same-origin and never use a bearer key.

- **2026-11-03 — Sort plans and preserved revisions:** user approved per-sort plans (default one named Round 1, custom names and optional keep presets, add future rounds anytime), mobile answer review and skip-to-end. Collections remain reusable card sets; sessions own ordered plans and runs remain round snapshots. Earlier answer changes after descendants exist create a new revised path; original decisions and downstream snapshots remain intact. Direct changes in the latest round preserve an audit trail and revision checks. Started round caps/counts are not silently altered by plan edits. Skips persist pending queue order without becoming decisions. Additive local SQLite/D1 migrations and both-runtime tests precede any separately authorized live migration/deployment.
- **2026-11-03 — Dark responsive cards:** user replaced the white card preference with dark navy/light text, direct finger-following movement, red left/green right intensity based on drag distance, threshold commit and snap-back. Preserve context scrolling and safe cancellation; drag feedback is local and only completed actions save.

- **2026-11-03 — Migration and audit parity:** existing parent chains are backfilled to root sort sessions before assigning foreign keys; historical branches retain actual keep caps while legacy plan presets use the maximum cap for each round number. Forks clone the complete decision audit graph and remap replacement links within the new path, enabling repeated Undo without touching original decisions. D1 child creation inserts under parent/plan CAS first and updates session revision only after that unique child exists; all in-place answer/Undo mutations recheck descendant absence. Parent lookups use an explicit index. These rules preserve history and reject concurrent changes without partial plan mutations.

## 2026-11-06 — Explicit portable library transfer

The owner approved manual bidirectional `.sift.json` import/export across the website and native app, superseding the earlier no-website-import boundary. Accounts, databases, and automatic sync remain independent. The versioned archive retains native immutable records and fixed snapshots; the web runtime keeps canonical records beside editable SQL projections. Every collection revision leaf is usable on the website, and per-version exports include the complete logical bundle. Imports are additive, previewed and atomic; identical records skip and conflicting bundles use stable alternate identities. No secrets, CloudKit state, or account bindings travel in a file.

Web histories preserve the decisions, undo/replacement links, snapshots and current pending order actually recorded by the website. Its prior schema has no chronological skip/plan-edit event stream; exported normalization actions describe the captured state and do not invent original event times. Recorded later-round caps may equal incoming card counts to preserve valid website histories; native creation retains its existing strictly reducing defaults. Transfer acceptance is local and synthetic; website deployment, D1 production migration and a new TestFlight upload require separate authorization.

## 2026-11-07 — Numeric card details and rating rounds

Numeric facts belong to immutable collection/card revisions; rating answers belong to a specific sort round and path. Collection-level field definitions use stable UUIDs with optional per-card values. Rating rounds carry a fixed named scale, never a keep cap; they retain all incoming cards for subsequent rounds. Explicit Save records an answer; slider movement is a local draft. Zero is distinct from unanswered. Started round type/scale are immutable. The protocol contract is shared with the other repository; new numeric semantics require record/archive v2 and new readers retain legacy v1 support. Historical payload bytes/IDs remain unchanged. Website SQL migration is additive and retains its original decision audit table. No production migration, deployment, upload or CloudKit schema action is authorized by this feature.
