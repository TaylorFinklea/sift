# Numeric card values and rating rounds
The website and native iPhone app share this contract. User approved both persistent card numeric details and rating rounds in website+iPhone. Keep dark navy/cyan design. No live provider/deploy/upload/device/Git push actions.

## Frozen cross-runtime JSON contract
NumericScale = { name: String, minimum: Number, maximum: Number, step: Number, unit: String }, default Rating/0/10/1/"". Bounds finite, abs <=1e9; minimum < maximum; step>0 <=range; at most 6 decimal places; grid relative to minimum with tolerance 1e-7 on quotient; max is valid only on grid. Names1..60 graphemes, unit<=16. Reject invalid nonfinite/offgrid values rather than clamping server-side.
NumericField = { id: UUID, ...NumericScale }. Collection numericFields optional array (max8 unique stable UUIDs); missing means []. Card numericValues optional object keyed field UUID containing only explicitly assigned valid numbers; missing means {}. Removing field deliberately removes draft values, historical snapshots untouched.
RoundPlanItem adds optional ratingScale (NumericScale, no ID). Absent -> existing keep/discard round; present -> rating round and keepLimit must be null. Started round scale/type is immutable just like keep caps; title may change.
SortDecision existing operation decided/revisedPath carries choice "rating" and optional value Number for rating. keep/discard must have no value. Session adds numericFields snapshot for fixed card values display; cards retain numericValues. Existing native enums add .rating, SortDecision.value optional. API choose/revise use {choice:"rating",value:Number}; rating decision only accepted in rating round. GET run has ratingScale (null if choice) and numericFields snapshot plus decisions.value only for ratings.
Rating round explicitly saves current slider/number value with Save rating; touching/previewing never commits. Initial draft unanswered; save disabled until explicit slider/number action. Zero is valid; no truthiness tests. Skip requeues, Undo restores replacement semantics, Review can change scores and earlier-round revisions preserve old paths. Results order high-to-low or low-to-high without changing card queue or recorded order.
Next round incoming after rating = ALL cards in same original round order. After choice = only keeps. Rating round cap internal sentinel may be cardCount but display/report keepLimit=null; ratingScale controls interpretation, never treat scores as keeps or show keep labels. Rating rounds can follow any completed round with >=2 incoming cards. Existing default keep round behavior unchanged.
Collections define fields then per-card slider+precise number optional editor. Display assigned card values on sorting/review.
## Storage/version compatibility
Preserve all existing immutable v1 bytes/IDs and records. New clients read schema/rules 1 and 2. Version2 for records/actions with new numeric/rating semantics so old clients fail closed instead of dropping values; old records still encode legacy shape/bytes (omit empty optional new fields). Archive v1 stays accepted; export v2 when any v2 record exists, otherwise1. Old app rejects v2. Envelope2 + record2 numeric history must roundtrip JS<->Swift including deterministic ID remap of field definition IDs and numericValues keys (ratingScale has no ID). Never rewrite UUID-like user text.
Native domain additions use existing atomic record+outbox repository and CKSyncEngine; no CloudKit schema/provider changes. Account/stale preview guards unchanged.
Web SQL: prefer additive new sort_answers table supporting choice rating/value, COPY original decisions once and retain original table untouched rather than dropping/rebuilding the self-referencing decisions table or pretending ratings are keep. New runtime consistently queries sort_answers; preserve original audit IDs/replacements and indexes. Add collection numeric_fields_json, run rating_scale_json + numeric_fields_json snapshot. Migration0005 before future deployment, but this task only local. Existing rows survive. Precise storage choice can be adjusted with lead if concrete constraint arises.

## Version-two conflict serialization

After rewriting typed UUID references, v2 bundles serialize payloads using the website's exact recursive sorted-tree algorithm and ECMAScript JSON.stringify, including its numeric formatting and integer-like key ordering. Native uses a local system JavaScriptCore context with a fixed trusted function and JSON passed solely as a call argument, with no host/network bridge. Errors reject the preview; no original-payload fallback is allowed under remapped IDs. Existing v1 conflict serialization remains unchanged. All accepted unused card revisions also validate their values against their own collection revision's field definitions.
