# Adversarial review findings

**P1 — `webWorkspaceToTransfer` can drop imported sort actions when a run is a `base` match but the collection content edited** (shared/transfer.js:609-615). Reproducer: import a bundle, edit *only* the collection's current title/description (no run changes), export. In `ensureRevision` the source `revisionCollections` map still has the original session revision, and the collection's current leaf gets a new ID (`current|...`). For each run row, `base = baseRows.find(id)` matches; `stableJSON(runDTO(base))===stableJSON(runDTO(row))` holds, so `checkpoint` is taken and `continue` is hit — fine. But `contextByRun.set` at line 684 only records `checkpoints`; `contextByRun` is built once from baseline and never updated to include the new `current` collection revision. The session still points at the old `collectionRevisionID`, whose collection revision is now no longer a leaf and whose content no longer matches current content, so later the "Current editable content must remain a leaf" check at line 692 forces `ensureRevision(collection, current|…)`. The exported session's `collectionRevisionID` still refers to the *old* revision, which is not the leaf, so on the next import the session snapshot is inconsistent with `current` and validation fails — data-loss only becomes detectable by a round-trip failure. Smallest fix: after line 692 `ensureRevision`, if `lastRevision !== sourceRevisionID` also rewrite or add a fresh sortSession for any session whose `collectionRevisionID` is now non-leaf, or skip the `base` fast-path when the collection content changed.

**P1 — Cloudflare `prepareD1Transfer` re-remaps already-remapped record IDs, causing double-remap collisions with conflictingIDs** (cloudflare/index.js:300-313 and shared/transfer.js:757). In `remapTransferBundleIDs`, `conflictingIDs` is validated but not used to skip already-colliding IDs; the `if` at line 757 returns the same `next` in both branches. If two import attempts both hit a conflict on the same source bundle, the second attempt remaps using a namespace that hashes the *original* record IDs (fine, deterministic), but the check at line 296-298 will see the incoming original records still conflict with what's now stored (which is the first remap). The remapped result is deterministic from the original, so second attempt computes the same remap and hits the same store conflict — `storedRemappedCount` will not equal length, so it's pushed into `conflicts` rather than `duplicates`, and `commitD1Transfer` will try to insert records whose IDs already exist → SQLITE constraint → user sees "That ID already exists" and import fails. Smallest fix: when the remapped bundle's records are all already stored as-is, treat as duplicate (already the intent at 309) — but the current check uses `existingRecords` keyed on `record.id` which after `validateTransfer` normalization are the *remapped* IDs, and `existing.ownerID === record.ownerID` will be false because stored owner was remapped with a *different* namespace. Compute namespace from the *stored* remapped record IDs, not the incoming ones, or check by payload equality only.

**P2 — `projectBundle` selects `collections[0].id` as fallback when a session's source revision is on multiple leaves** (shared/transfer.js:411). If a collection has two leaves sharing a common ancestor that a session was recorded against, `collectionForRevision` returns `collections[0].id` — the lex-first leaf, which may not be the branch the user actually selected. On export the run is silently attached to the wrong editable collection and its `revisionCollections`-based parent becomes wrong on re-import, producing `sortSession.collectionRevisionID` pointing at a revision under a *different* leaf; on re-import `webWorkspaceToTransfer`'s `ensureRevision` for that view sees `sourceView` from a different leaf and `hasLaterResults`/queue reconstruction diverges. Smallest fix: when `candidates.length !== 1`, fail with a deterministic "ambiguous source revision" error rather than silently picking one, since the format spec at line 17 says "Sessions with an unambiguous source version attach to that editable row; shared-ancestor history stays on the primary row" — a shared-ancestor session should attach to nothing editable, not a random leaf.

**P2 — `replayPath` accepts a `revisedPath` whose `_0` decision's `replacesActionID` points at an action not in `seen`** (shared/transfer.js:339). Line 339 checks `target?.action.id !== op._0.replacesActionID` where `target = effective(n).get(cardID)` — that only confirms the *current* effective target matches. It does **not** check `seen.has(op._0.replacesActionID)`, unlike the Swift `SortProjectionBuilder` at Replay.swift:211-214 which requires `seen.contains(targetID)`. A crafted archive where `replacesActionID` points at a sibling branch's action that is effective in round n but was undone-by-replacement on the replay path can pass JS validation but fail Swift replay. Reproducer: build two branches; on branch B undo A's decision by replacement, then on branch B add a `revisedPath` targeting the pre-replacement action. JS accepts, Swift `SortProjectionBuilder` rejects (`validateReplacement` requires `seenDecisionIDs.insert` on a decision whose `replacesActionID` is in `seenActionIDs` — but the target of `revisedPath` is validated via `effectiveDecisions`, and the *original* `replacesActionID` is never checked against `seen`). Smallest fix: after computing `target` at line 339, also `if (!seen.has(op._0.replacesActionID)) invalid();` — align with Swift's stricter check.

**P2 — `webWorkspaceToTransfer` `planEdited` guard uses `state.activeRound` but the row being edited may be an earlier round on a fork** (shared/transfer.js:353 vs 623/669). At line 623, a `planEdited` is added only `if (!fork && stableJSON(targetPlan) !== stableJSON(state().plan))`. On a fork (`fork === true`), `state()` reflects the source branch's current plan; the row's `roundPlan` is captured but not applied via `planEdited` before the roundStarted/revision decisions are replayed, then at line 669 another `planEdited` is attempted *after* the fork decision. If the target round's plan differs from the source's plan at that time (e.g. user changed round titles on the fork), the post-fork `planEdited` at line 669 rejects because `state().plan[0..activeRound-1].keepLimit` must match — but titles are not checked, so it would succeed for title-only changes yet fail for keep-limit changes on already-started rounds per line 353. Smallest fix: for a forked row whose `targetPlan` differs in already-started rounds' keep limits, the archive cannot be represented — fail explicitly at line 669 with a clear message ("Web edits to plan limits on started rounds of a revised path cannot be exported") instead of a generic `invalidActionGraph`-derived error, so users aren't left with an unexportable workspace. (Only a limitation if documented; but the current behavior is a silent `fail` mid-export, losing the whole archive.)

No additional material P1/P2 beyond those five. File picker, bounded iOS read, D1 reimport remap collision (per reviewer's earlier note) and missing-sync-schedule issues appear repaired in this packet.
